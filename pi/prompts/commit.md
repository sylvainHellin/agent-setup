## Identifying session-modified files

You know which files you edited or created during this conversation. Use ONLY those files. If you are unsure whether a file was touched by you, check your conversation history for Edit/Write tool calls on that file.

Run `git status --porcelain` and `git diff --stat` to see the current working tree, then cross-reference against your memory of files you touched.

## Commit strategy

1. Run `git log --oneline -10` to match the repo's existing commit style.
2. If the session touched a small, coherent set of changes: create a single commit.
3. If the session made logically distinct changes (e.g., refactor + new feature + config change): split into multiple atomic commits, most foundational first. Each commit should be self-contained and pass tests on its own.

## For each commit

1. Stage ONLY the relevant files: `git add <file1> <file2> ...` (never `git add -A` or `git add .`).
2. Write a commit message using a HEREDOC:
   - Summary line: imperative mood, under 72 characters, no trailing period.
   - Body (when needed): blank line after summary, wrapped at 72 chars, explains *why* not *what*.
3. Run the commit:
   ```bash
   git commit -m "$(cat <<'EOF'
   <summary line>

   <body if needed>
   EOF
   )"
   ```
4. Verify with `git log --oneline -1`.
