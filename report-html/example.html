Why the cron job has to go

The import runs once at 02:00 and processes every file uploaded during the day in one Python process. Three problems have become regular:

  • A single malformed file stops the whole run, and the remaining files wait a full day.
  • The run now takes 3 h 40 min and overlaps with the 06:00 backup on most Mondays.
  • Users who upload in the morning see their data only the next day.

A job queue imports each file as soon as it arrives, retries failures one file at a time, and scales by adding workers.

How the Postgres queue works

Claiming a job

Each worker claims the oldest due job in one statement. SKIP LOCKED lets concurrent workers pass over rows another worker holds, so two workers never take the same job.

UPDATE import_jobs
SET status = 'running', attempts = attempts + 1, started_at = now()
WHERE id = (
  SELECT id FROM import_jobs
  WHERE status = 'queued' AND run_after <= now()
  ORDER BY run_after
  FOR UPDATE SKIP LOCKED
  LIMIT 1
)
RETURNING id, upload_id;

Worker loop

while True:
    job = claim_job(conn)
    if job is None:
        wait_for_notify(conn, "import_jobs", timeout=30)
        continue
    try:
        import_file(job.upload_id)
        mark_done(conn, job.id)
    except Exception as exc:
        retry_later(conn, job.id, error=str(exc))  # backoff: 1, 5, 30 minutes

A LISTEN/NOTIFY pair wakes idle workers when a job arrives, so they do not poll the table.

If the queue ever needs more than a thousand jobs a minute, we move to RQ; the job table stays as the record of what was imported. Design review, 12 January 2026

What we gain

  • Files import within a minute of upload.
  • A failed file retries alone, three times, then lands in a list for a human.
  • The job history is a table we can query with SQL.

What we give up

  • Scheduling features Celery has built in, such as rate limits per task type.
  • A ready-made monitoring dashboard; we add two panels to the existing one.
  • Headroom above about 950 jobs a minute without further work.

Load test setup

Staging database on the same instance size as production, four workers on one host, 5,000 synthetic files of 2 MB each, queued in one burst. Each option ran three times; the table shows the median.

Risk: table bloat

A queue table with many updates per row grows dead tuples quickly. Finished jobs move to an archive table every night, and the table gets its own autovacuum settings.

Prototype done

The prototype on staging imported the 5,000-file burst in 5 min 15 s with no duplicate and no lost job.

Decisions for you

  1. Adopt the Postgres queue table for the import service (recommended), or go straight to RQ with Redis.
  2. Keep the cron entry disabled but in place for one month as a rollback path (recommended), or remove it with the migration.
